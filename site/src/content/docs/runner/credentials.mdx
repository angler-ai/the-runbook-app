Open **Settings › Organization › Runner › Credentials** and choose **Add credential**. Select the type, enter the destination settings, and decide which projects can use it. Sharing starts at **none**.

| Type | Secret field | Destination and delivery |
| --- | --- | --- |
| `api-key` | `key` | The gateway adds a header to requests to the declared hosts. |
| `model-provider` | `api_key` | The gateway adds the key to requests to the bound provider and endpoint. |
| `mcp-bearer` | `token` | The gateway adds the bearer token to requests to the bound MCP server URL. |
| `mcp-oauth` | `client_secret` for a pre-registered confidential client | The vault exchanges and refreshes tokens. The gateway receives only the access token for a live release. |

New model provider keys default to `read`. New API keys, MCP bearer tokens and OAuth connections default to `destructive`. Review the label against the upstream
permissions before binding a credential to an agent. Existing labels carry
over when you upgrade.

Check the destination shown in the form before you enter the secret.
The browser verifies the ingest key against the registered vault identity,
then seals the secret to that key. The core and runner API relay the sealed value. The vault checks the binding and version before storing it, and returns metadata such as a fingerprint. Use **Test connection** to check the binding. If the test fails, the result gives an error class such as unauthorized or unreachable.

## Use a Google Secret Manager reference

API keys, MCP bearer tokens, and model provider keys can reference a secret
already in Google Secret Manager. Set the source in the credential's config
and confirm the reference with the vault's sealed secret flow.

```json
{
  "secret_source": {
    "type": "gcp-secret-manager",
    "resource": "projects/my-project/secrets/upstream-key",
    "version": "latest"
  }
}
```

Use `"latest"` to pick up rotations on the next release or renewal. Use a
positive version number, such as `12`, to pin a version. The API normalizes
version numbers to decimal strings.
Changing the resource or version changes the binding and requires a fresh
sealed confirmation. When using the API, the existing secret field takes a
seal of the canonical JSON reference. Confirm the reference before testing.

The vault reads the value using its own Application Default Credentials and
holds it in memory for delivery to the gateway. The runner database stores
the reference and its confirmation metadata. The runner logs attempts as
`credential.secret_manager_access` and records the concrete version read,
including when the reference uses `latest`. During grant renewal, transient
Secret Manager failures are retried while the current material remains valid
until the existing grant expires. Denied access and missing or disabled
versions end the release.

Set `RUNNER_SECRET_MANAGER_RESOURCES` for the vault to a JSON array of
deployment policy entries. For example:

```json
[
  {
    "resource": "projects/my-project/secrets/upstream-key",
    "types": ["api-key"],
    "destinations": ["api.example.com", "uploads.example.com"]
  },
  {
    "resource": "projects/my-project/secrets/mcp-token",
    "version": "12",
    "types": ["mcp-bearer"],
    "destinations": ["https://mcp.example.com/tenant"]
  }
]
```

List all permitted hosts for an `api-key`, the full MCP URL for an
`mcp-bearer`, or the full endpoint for a `model-provider`. Destinations
match exactly after normalizing them the same way as the credential.
Every destination on a credential must match a single policy entry. Omit
`version` to allow any supported version selector, or set it to require the
exact selector, such as `"12"` or `"latest"`. Use separate entries when
credential types need different destinations. The vault enforces the policy
at seal, test, release, and renewal. Only the deployment operator can change
it. Replace legacy comma-separated resource lists with JSON before
restarting the vault. Use `[]` to disable references.

On GKE, set `runner_secret_manager_secret_ids` in Terraform to the same list
of objects, using full resource names in the deployment project. Terraform
rejects startup secrets and grants the vault access on each listed secret.
Run `terraform output -raw runner_secret_manager_resources` and put the
resulting JSON string in the vault's mounted process JSON. For Docker, give
the vault Google Application Default Credentials and grant its identity
`roles/secretmanager.secretAccessor` on each selected secret.

Enable Secret Manager Data Read and Data Write audit logs in the projects
that own the secrets. By default the GKE module leaves existing audit policy
in place, including policy previously created by the module. Set
`manage_secret_manager_audit_config = true` only if you want Terraform to
take ownership of the deployment project's Secret Manager service policy
and replace it with Data Read and Data Write logging. To transfer management
away after opting in, remove the audit resource from Terraform state before
disabling the option so the policy stays in place.

## Use a credential from a CLI in a sandbox

Map a variable such as `GH_TOKEN` to a proxy-delivered API key through the
environment's `credential_env` setting. The sandbox receives a placeholder.
The gateway replaces the bound header on requests to the credential's
configured hosts using the credential released for the step. Model and MCP
credentials use their respective delivery paths.

## Connect an OAuth MCP server

1. In **Credentials**, add an **MCP OAuth** credential with the exact MCP URL. Choose dynamic or pre-registered client registration and enter the scopes and authorization parameters the provider requires.
2. Choose **Discover OAuth endpoints**. Review the resource, issuer, and the full authorization, token, registration, and revocation URLs. The discovered endpoints are saved with the credential. Choose **Confirm endpoints** to accept them and, for a dynamic client, register it once. For a pre-registered confidential client, enter its client secret in the credential's secret field after confirming.
3. Choose **Connect** and verify a fresh second factor. Complete consent in the same browser with the account whose access the agents should share. Review the vault-signed account details and confirm them in the same Runbook browser session. If the provider gives no account details, choose **Confirm without a reported account**. The vault tests MCP initialization and tool discovery after confirmation. The credential shows the scopes granted, any account details the provider returns, and a warning before an access-only or hard expiry.
4. In **MCP servers**, add the same URL and select or enter the OAuth credential ID. Discover and review the tools, then pin the snapshot. Label the credential and each tool according to what they can do. Unlabeled tools and newly created OAuth credentials default to `destructive`. Share the server and credential only with the projects that need them, and pin the allowed tools in the agent version.

The redirect URI is specific to the credential. Copy it from the confirmed configuration when a provider requires an allow-list.

```text
https://RUNBOOK_ORIGIN/v1/runner/oauth/callback/CREDENTIAL_ID
```

Use **Reconnect** after a grant expires or the provider invalidates it. Use **Disconnect** to fence live releases and revoke the grant. If upstream revocation fails, revoke the grant in the provider's account settings. Use `credential.oauth_refresh_failing` to receive a webhook after one hour of continuous refresh failures. After 24 hours the credential requires reconnection. The vault retries transient failures with capped backoff and keeps a still-valid token available during a scheduled refresh failure. Client authentication failures such as `invalid_client` require immediate reconnection. Subscribe to `credential.reconnect_required` and `credential.oauth_expiring` for those state changes.

The vault signs the account details from the bound HTTPS token endpoint. The confirmation shows the provider's display name with its stable account or workspace ID when available. For Notion, it also includes the email domain and bot ID when returned. If the provider has no stable ID, a name change is shown as an account change and must be confirmed. Control characters and bidirectional overrides are stripped from display names. Failed callbacks handled by the vault and failed exchanges record an audit event with the error class. The vault log includes the provider HTTP status when available. If the response supplies an ID token as the only source of account information, the vault uses its `email` and `sub` claims when present. The application does not check the ID token signature because it receives the token directly over TLS from the bound token endpoint and uses it only as display metadata.

The vault attempts to revoke unconfirmed grants when they expire, are restarted, or are disconnected. An access-only grant requires two rejection reports at least 30 seconds apart and within five minutes. A successful MCP request or connection test clears that window for the same token.

A signed authorization proof lasts ten minutes. The core and CLI allow up to two additional minutes for the vault clock to be ahead. If the proof falls outside the accepted window, sync the affected clocks and restart authorization.

### Notion

Use `https://mcp.notion.com/mcp`, Streamable HTTP, and dynamic registration.
Set the authorization parameters to `{"prompt":"consent"}`. Give the dedicated
Notion account access to the pages the agent should use and check the returned
workspace before sharing the credential. Notion rotates refresh tokens and
caps the grant at about 180 days. Reconnect before the hard expiry. The vault
reuses the registration on reconnect. [Notion MCP client guide](https://developers.notion.com/guides/mcp/build-mcp-client)

### Angler MCP

Use the Angler deployment's Streamable HTTP MCP URL and dynamic registration.
Set the scopes to `openid email` and the authorization parameters to
`{"access_type":"offline","prompt":"consent"}`. An Angler operator must
add the exact redirect URI to `ALLOWED_REDIRECT_URIS` and deploy that change
before consent. Connect a dedicated Workspace account in an allowed domain
with no unrelated access. Label Angler write tools `destructive`.

Angler currently returns a Google bearer usable at Angler MCP and Google's
UserInfo endpoint until it expires. Disconnecting revokes the account's Google
grant for that client, which can affect other uses of the same grant.

### Meta Ads MCP

Start with an Employee-role Meta system user. Assign only the ad accounts and
asset tasks the agent needs. Generate a token with `ads_mcp_management` and
`ads_read` or `ads_management`, as appropriate. Store it in an
`mcp-bearer` credential bound to `https://mcp.facebook.com/ads` and add the
server with Streamable HTTP. [Meta Ads MCP setup](https://developers.facebook.com/documentation/ads-commerce/ads-ai-connectors/ads-mcp-server/ads-mcp-server-get-started)

For OAuth, create a Meta app with the **Create & manage ads with ads MCP
server** use case and register the per-credential redirect URI in **Facebook
Login for Business**. Use pre-registered mode with the app ID and the token
authentication method the app supports. Verify public-client PKCE support,
refresh availability, token lifetime, and a real tool call with your app
before relying on OAuth. [Meta Ads MCP setup](https://developers.facebook.com/documentation/ads-commerce/ads-ai-connectors/ads-mcp-server/ads-mcp-server-get-started)

### OAuth with the CLI

```sh
runbook runner credential discover "$CREDENTIAL_ID" --json
runbook runner credential confirm "$CREDENTIAL_ID" --binding-pin "$DISCOVERY_HASH"
runbook runner credential connect "$CREDENTIAL_ID" --binding-pin "$REGISTERED_HASH"
runbook runner credential disconnect "$CREDENTIAL_ID"
```

The discovery hash covers the endpoints before registration. The registered
hash also covers the assigned client ID. Obtain that hash from the confirmed
configuration on a trusted client. The connect command prints a Runbook URL
and waits for browser approval. Open the Runbook URL as the same person and
choose **Connect**. The CLI verifies the signed authorization and prints the
provider URL to open in that same browser. After consent, review the returned
provider account and choose **Confirm account and connect**. The provider must
return an identifiable account to activate the grant.

Use `confirm --reset-registration` after reviewing the endpoints again if a
dynamic registration ended without a definite result. The provider may retain
the earlier registration. Disconnect reports **Pending gateway purge** and the
remaining access lifetime when the vault cannot confirm the fence yet.

## Enter a secret with the CLI

Check the [vault identity](/runner/setup/#verify-the-vault-identity) before sealing the first secret. Run `runbook runner credential types --json` to see the supported types, config fields and secret field names. Create metadata from a local JSON file containing `name`, `type`, `config` and `groups`. Add the desired `label` and `sharing` when creating it. For example, use `{"projects":["PROJECT_ID"]}` for sharing and set `groups` to the allowed group IDs or `"all"`. Keep the secret in a separate protected file or enter it at the prompt.

For example, save model-provider metadata as `credential.json` and substitute the allowed group and project IDs.

```json
{
  "name": "Primary model key",
  "type": "model-provider",
  "config": {"provider": "anthropic", "endpoint": "https://api.anthropic.com"},
  "groups": ["GROUP_ID"],
  "label": "read",
  "sharing": {"projects": ["PROJECT_ID"]}
}
```

```sh
runbook runner credential create --file credential.json --json
runbook runner credential set "$CREDENTIAL_ID" "$FIELD"
runbook runner credential test "$CREDENTIAL_ID"
```

Use the returned credential ID and the field name from the table. The CLI verifies the ingest key against the registered vault identity and displays the normalized destination for confirmation before reading the value from a hidden prompt. An independent ingest-key fingerprint can be supplied with `--pin`. The ingest key rotates and has a different fingerprint from the vault identity.

For standard input, supply a local file containing the expected `type`, `config` and `groups`, or pin the independently verified destination `binding_hash` from credential creation. The CLI checks the destination before reading the value.

```sh
runbook runner credential set "$CREDENTIAL_ID" "$FIELD" \
  --expected-config credential.json < "$SECRET_FILE"
# Or provide a verified destination hash.
runbook runner credential set "$CREDENTIAL_ID" "$FIELD" \
  --binding-pin "$BINDING_HASH" < "$SECRET_FILE"
```

Use `runbook runner credential label "$CREDENTIAL_ID" read` to change the label after reviewing the upstream permissions. Use `runbook runner credential share "$CREDENTIAL_ID" --file sharing.json` with `{"sharing":{"projects":["PROJECT_ID"]}}` to replace the full project-sharing list. If a change returns a `proposal_id`, have the appropriate administrator approve the proposal before using the new access.

MCP servers and hosts that agents reach through the gateway must be public `https` addresses on port 443. The gateway refuses private, loopback and link-local addresses.

Use a different credential for each set of permissions and destinations. Where possible, use read-only credentials and scope them to the smallest set of resources the agent needs. Sharing a credential makes it available for a project admin to bind to agents. A project editor can steer an agent that already has the binding.

Use **Replace** in the credential form to rotate a value. Changing the destination binding requires a fresh seal for that binding. **Revoke** stops the runner from issuing releases and invalidates active releases. Rotate the value at the provider if you suspect exposure.
**Delete** removes the credential from the catalog and destroys its stored
key material in the live vault. Backups with the old wrapped keys retain it
until they expire.

See [security boundaries](/runner/security/#entering-secrets) for the scope of browser sealing.
